# Scheduler Policy Analysis

**Status:** Implemented (Session 26). Interchangeable scheduling policies behind `SchedulerPolicy` with comparative embedded benchmarks.

**Not implemented:** Scheduler optimization, predictive scheduling, ML-driven scheduling, adaptive scheduling.

## Architecture

```
SchedulingCycleRunner
        │
        ▼
QueueReader.list_queue_items()
        │
        ▼
items_to_candidates()  ──► SchedulingCandidate metadata
        │
        ▼
SchedulerPolicy.evaluate()  ──► SchedulingDecision list
        │
        ▼
BatchService.place_selected()
```

`SchedulingCycleRunner` depends on `SchedulerPolicy`, not a concrete selector. Policy is selected via `Settings.scheduler_policy_id` and `build_policy()`.

## Policy definitions

### FIFO (`fifo`)

- Order: `queue_position`, then `enqueued_at`
- Baseline; deterministic; no cross-request state
- Limitation: ignores job size and latency pressure

### Shortest job first (`shortest_job_first`)

- Order: `estimated_job_tokens` ascending
- Estimation: `estimated_input_tokens + max_tokens` (input via chars/4)
- Assumption: smaller bounded output implies shorter service time
- Limitation: heuristic only; mock backend does not vary execution time by size

### Latency-aware (`latency_aware`)

- Score: `queue_wait_duration_ms / queue_objective_ms + request_age_ms / age_objective_ms`
- Select highest score first
- Config: `SCHEDULER_LATENCY_QUEUE_OBJECTIVE_MS` (default 100), `SCHEDULER_LATENCY_REQUEST_AGE_OBJECTIVE_MS` (default 5000)
- Limitation: static objectives; not per-tenant SLO configuration

### Fairness (`fairness`)

- Ratio: `selection_count[priority_class] / weight[priority_class]`
- Select lowest ratio; tie-break by higher `queue_wait_duration_ms`
- Weights: `SCHEDULER_FAIRNESS_ELEVATED_WEIGHT` (3), `DEFAULT` (2), `BACKGROUND` (1)
- Limitation: fairness dimension is `priority_class` only; state is in-process per policy instance

## Candidate metadata

`SchedulingCandidate` fields used by policies (from `queue_item_to_candidate`):

| Field | Source |
|-------|--------|
| `queue_wait_duration_ms` | `now - enqueued_at` |
| `request_age_ms` | `now - request_context.arrival_time` |
| `max_tokens` | `inference_request.max_tokens` |
| `estimated_input_tokens` | sum(message chars) / 4 |
| `estimated_job_tokens` | input estimate + max_tokens |
| `priority_class` | queue item or inference request priority |

## Telemetry

Per decision (selected and skipped):

- Structured log events: `request_selected`, `request_skipped` with `scheduler_policy_id`, `queue_wait_duration_ms`, `request_age_ms`
- Prometheus:
  - `gpu_inference_scheduler_policy_decisions_total{policy_id, selected, decision_reason}`
  - `gpu_inference_scheduler_policy_queue_age_seconds{policy_id}`
  - `gpu_inference_scheduler_policy_request_age_seconds{policy_id}`

## Comparison methodology

Session 26 benchmarks (`benchmarks/runner/policy_comparison.py`):

1. Fixed continuous batching (`max_batch_size=4`, `admission_window_ms=50`)
2. Mock backend, model `demo`
3. Workload alternates short (`max_tokens=32`) and long (`max_tokens=256`) requests
4. Priority cycles DEFAULT / BACKGROUND / ELEVATED
5. Staggered `arrival_time` by 25 ms per index for latency-aware differentiation
6. Only `scheduler_policy_id` changes between runs

Scenarios: `scheduler_policy_c4`, `scheduler_policy_c8`.

Report: `benchmarks/reports/scheduler-policy-analysis.md` (generated by `policy_validation.py`).

Validation: `python runtime-validation/policy_validation.py`

## Measured observations

See `benchmarks/reports/scheduler-policy-analysis.md` after validation run. Numbers are host-specific; do not treat as production GPU results.

## Limitations

- Policies affect selection order only; batch admission and dispatch rules are unchanged
- Mock backend execution time does not reflect job-size heuristics
- Fairness policy counters reset on new scheduler application instance
- No HTTP load-test integration for policy comparison in CI
- vLLM-backed policy benchmarks are operator-run only (not automated in Session 26)
